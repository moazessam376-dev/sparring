# Surveying a large repository for a learner-facing project map

Date: 2026-09-12. Question: how should an AI agent survey a repository that is too large to read in full, select architecturally important material, verify its claims, and show incomplete coverage honestly? Primary research papers, official specifications, and public source code are cited as [S#]. Review papers and abstract-only records are labeled in the source list; secondary summaries are not used for numerical claims.

## Findings

### 1. The selection target is architectural evidence, not maximum reading coverage

The survey described in section 6 of the sparring design is a claim-producing operation. It must produce a small graph of parts, interactions, and cross-cutting constraints, then open doors to deeper lessons and concept cards. That makes the right objective different from “summarise the most files” or “retrieve the files most similar to the prompt.” The useful unit is an atomic claim with evidence: a module has a responsibility; an entry point reaches it; an edge crosses a boundary; a constraint is enforced at a particular location; or a change regularly couples two areas.

Popularity is a weak proxy for that objective. A file can be popular because it is a utility, generated artifact, test fixture, or frequently edited configuration file. Architectural importance is better supported when several independent signals agree: reachability from an executable or public entry point, verified static dependencies, bridge-like position between otherwise separate communities, a high-cohesion module boundary, a repeated cross-cutting change pattern, and an explicit build or deployment role. Ownership and centrality are useful prioritisation signals, but neither is sufficient evidence for a node sentence.

The practical consequence is that selection needs two stages. The first stage builds a cheap, repository-wide structural inventory. The second spends context on a small set of candidate regions and their graph neighborhoods. A model should not be asked to infer the inventory from a single prompt containing a large concatenation of files. The map should be a compressed view of an evidence graph, not the only copy of the agent’s reasoning.

### 2. Retrieval and code search find task-relevant files, but architecture labels are rarer

The 2024–2026 repository-retrieval literature provides strong evidence that retrieval should be multi-stage and structure-aware, but most evaluations label relevance by whether a file was edited for a task. That is useful evidence for debugging or change location, not a direct measure of architectural importance.

Repoformer showed that selective retrieval can improve repository-level code completion efficiency: it reported up to 70 percent inference-speed improvement without lowering completion performance [S1]. DraCo added an import and data-flow graph to retrieval and reported a 3.43 percentage-point exact-match improvement and a 3.27 percentage-point identifier-F1 improvement on Python repository completion [S2]. GraphCoder used control-flow and dependency information for coarse-to-fine retrieval; it beat the compared RAG systems on 15 of 20 repositories. Removing control-flow information caused average relative drops of 19.82 percent for code-match exact match and 15.64 percent for identifier exact match [S3]. These results support graph expansion and selective retrieval. They do not show that the retrieved files are the system’s architectural centers.

Gandhi, Gao, and Callan provide the clearest large-repository retrieval measurement. On seven large repositories and 3,500 test queries, BM25 over commit messages reduced more than 10,000 files to about 1,000 candidates; a commit reranker reduced this to hundreds, and a source-code reranker reduced it to tens. The full pipeline had mean average precision 0.270, mean reciprocal rank 0.434, precision at one 0.280, and recall at 100 0.590. BM25 alone had recall at 1,000 of 0.951 [S4]. This is a good engineering pattern: cheap high-recall filtering followed by increasingly expensive ranking. Its labels are files edited by the target commit, and the paper explicitly notes that not every edited file is necessarily relevant. It therefore measures change-task retrieval, not architecture recovery.

The 2026 Agent Retrieval Bench is a useful warning against assuming that a sophisticated model will discover the right region unaided. It contains 427 samples over 25 repositories, 308 repository snapshots, about 392,000 files, and 7.9 million chunks. No retrieval family dominated. The best reported embedding result, Qwen3-Embedding-8B, had Recall@20 of 0.7029. At the logged agent’s context budget, agents missed all gold files on roughly 27–35 percent of samples, and score thresholds did not reliably improve abstention [S5]. SWE-Explore similarly finds that agentic repository exploration can beat classical retrieval on 848 issues from 203 repositories in ten languages, while stressing coverage and context efficiency as separate problems [S6]. For sparring, “not found” must remain distinct from “does not exist.”

StackRepoQA gives a more repository-specific result. Its benchmark contains 1,318 real developer questions and accepted answers across 134 Java repositories. File retrieval scored around 5.66 on its answer metric, while graph retrieval averaged 6.12, with a reported significance of p < 0.0002; the best systems were around 64 percent rather than fully reliable [S7]. The authors also report no systematic relation between repository size or popularity and QA accuracy, and caution that high scores can come from verbatim overlap with Stack Overflow answers. CodeRepoQA’s 585,687 multi-turn examples likewise found a medium context condition stronger than a 100-percent context condition on its combined text-similarity metrics: 0.1698 versus 0.1518 [S8]. These results support bounded, selective context and graph-aware expansion, but they do not license a confident architectural map from retrieval scores alone.

The selection policy should therefore rank a candidate using separate columns rather than one opaque score. At minimum, keep lexical and semantic relevance, graph reachability, bridge or boundary evidence, build/configuration evidence, recent change coupling, and ownership risk separate. A region that is high on only one column is a candidate for inspection, not a confirmed map node.

### 3. Import graphs are a cheap structural backbone; call graphs need an explicit unknown state

The first repository-wide graph should be deterministic. Parse package manifests, build files, language imports, module declarations, exported symbols, and generated-source declarations. Store file, symbol, module, containment, import, inheritance, call, test, configuration, and build/deploy edges with the extractor and its version. Tree-sitter-based typed graphs are already used in SWE-QA: its graph contains repositories, files, code snippets, classes, methods, attributes, functions, parameters, and variables, with containment, calls, callers, and imports [S9]. The point is not to copy that schema exactly, but to make the evidence objects queryable before an LLM writes prose.

Import and build graphs are usually more reliable for module boundaries than call graphs. A static call graph can miss dynamic dispatch, reflection, dependency injection, registration tables, generated code, runtime plugin loading, and language-specific metaprogramming. An absent edge must therefore be recorded as unresolved rather than treated as a negative fact. The “Do Code LLMs Do Static Analysis?” study tests call graphs, AST properties, and data-flow questions across Java, C, and C++ models and finds that code LLMs are poor at static analysis [S10]. This is direct evidence for using parsers and analyzers for graph facts and using the model to interpret the resulting facts.

A claimed call path should be classified as one of three things: a statically verified path; a possible path containing unresolved dynamic edges; or a path not found in the analysed graph. Only the first can be phrased as a definite interaction on the learner’s map. Runtime traces, integration tests, framework metadata, and registration/configuration inspection can upgrade a possible path, but should not silently turn it into a static fact.

### 4. Clustering recovers candidate modules, but directory structure and cohesion must be compared

Module discovery can combine graph connectivity, directory hierarchy, names and comments, and architectural vocabulary. The recovery literature does not support a single universally best clustering method. StructSAR evaluates dependency-only and folder-aware structure across 11 open-source Java and C/C++ systems, including Hadoop, Lucene, Bash, Chromium, and OpenHarmony. Its central result is that folder information can improve weak-cohesion cases but can also pull the result away from dependency-only modularity; different systems and metrics favor different combinations [S11]. A directory is therefore evidence of intended organization, not proof of a module boundary.

HGEN is a related primary study of dynamically generated document hierarchies. It clusters source artifacts and uses trace links to organize them into a hierarchy. Against manually identified concepts, its reported concept coverage was 87.5, 84.4, and 100 percent across three systems, compared with 6.3, 37.8, and 50 percent for the baseline; trace-link mean average precision was 94.0–96.7 percent, and orphan artifacts fell from 17, 28, and 11 to 0, 9, and 1 [S12]. These are promising measurements for organizing documentation, but they measure concept and link recovery in the studied setting, not factual correctness of a learner-facing architecture sentence.

For sparring, a candidate boundary should be supported by a compact cut report: the number and weight of internal versus crossing imports/calls, the build-declared modules, the directory/name evidence, and the unresolved-edge count. The agent should be allowed to keep a large cohesive cluster at a second level if no defensible cut appears. Forcing exactly twelve top-level components would manufacture architecture.

### 5. PageRank and other centrality measures are useful for triage, with unusually good architecture-grounded evidence in one study

Centrality is a sensible way to find files or symbols that connect many parts of a dependency graph, but raw degree mostly finds popular hubs. Weighted PageRank, betweenness, bridge scores, and reachability from roots should be computed on the repository’s internal graph, not on stars, download counts, or external references.

A 2025 empirical study of key-class prediction is unusually relevant because its labels were grounded in architecture documentation rather than only commit frequency. Across 18 open-source Java projects, weighted network metrics, including weighted PageRank with damping factor 0.85, improved within-project key-class prediction. Weighted metrics beat design metrics in as many as 10 of 18 projects, and a combined network-plus-design model won 14 of 15 pairwise comparisons [S13]. This supports centrality as one architectural signal. It does not show that PageRank alone identifies the right learner-facing nodes, and the transfer results favor design metrics more than raw network metrics across projects.

Use centrality to allocate reading budget, not to write “important” into the map. A low-centrality bridge, entry point, configuration seam, or policy enforcement point can be architecturally more important than a high-centrality utility. The survey should preserve the reason a candidate was selected, so the learner can distinguish “central because many modules depend on it” from “selected because it is an operational root.”

### 6. Build, configuration, and deployment files provide high-value entry-point evidence

Entry-point discovery should begin with the repository’s executable declarations. Maven’s reactor model defines modules and dependency sorting [S14]. npm package metadata identifies package entry points through fields such as `main`, `exports`, `bin`, scripts, and workspaces [S15]. Python packaging defines entry points for console scripts and plugin discovery [S16]. Docker Compose describes services, dependencies, commands, health checks, networks, and volumes [S17]. Similar evidence exists in CI workflows, deployment manifests, server registrations, application factories, CLI routers, and test runners.

These files often identify the architecture the user actually runs, so they have stronger architectural evidence than popularity. They are not complete: profiles, environment conditions, generated manifests, reflection, and deployment overlays can hide paths. The agent should enumerate configurations and profiles, state which ones it inspected, and record unresolved variables. A dry-run or test execution can corroborate reachability, but a passing build is not proof that every claimed boundary or constraint is real.

A 2025 comparison of microservice architecture-recovery tools illustrates both the value and the limit. Across 17 Java/Spring applications, one component-recovery result reached precision 0.97, recall 0.98, and F1 0.98 for 182 components, but connection recovery was weaker; the best reported connection F1 values were 0.79 and 0.66 in the compared settings [S18]. Finding the services is easier than proving all of their interactions. Sparring should show the same distinction.

### 7. Change coupling reveals hidden logical dependencies, while ownership reveals knowledge risk

Version history is particularly useful for cross-cutting bands. A 2019 large-scale study of 133 popular GitHub projects found six recurring co-change patterns covering 1,719 clusters, or 95 percent of the studied clusters. It reported that 80–90 percent of co-changed function pairs shared calls, variables, or similar statements, and its CoRec approach reached 73–78 percent accuracy [S19]. Co-change is therefore often more than coincidental editing, but the result is still an association, not proof of a runtime dependency.

CoChangeFinder studies 66 projects, including OpenStack, OpenDaylight, Android, Chromium, and Qt. It reports that 16–33 percent of reviews contained a function that needed change but was not initially changed. Its graph model improved top-k accuracy by 3.44–40.45 percent, recall by 2.00–26.07 percent, and mean average precision by 0.04–0.21 over its baselines; delayed co-changes had a median delay of three review iterations and eleven days [S20]. This is strong evidence that history can expose maintenance-relevant hidden coupling. It is not evidence that two files belong in the same architectural node.

More recent work on co-committal strength across five large repositories and more than 14,000 commits finds that the signal is project-specific and affected by coding style and activity [S21]. The implementation should filter formatting, vendored, generated, release, and mass-renaming commits; use time decay; and retain the raw commit examples. A band should say “often changed together” unless a separate static or runtime analysis proves the stronger claim.

Truck factor and ownership metrics answer a different question: who has the knowledge needed to change an area? Avelino and colleagues analyzed 133 GitHub projects, more than 373,000 files, 41 million lines, and more than two million commits; 65 percent of the projects had a truck factor of two or less [S22]. Bus Factor Explorer processed 935 repositories, used the latest 1.5 years with a five-month decay half-life, excluded bots, and reported processing 12,000 commits in 25 seconds [S23]. These are useful for prioritizing learner topics, warnings, and questions about concentrated knowledge. The 2024 review of software ownership literature found only three of 79 papers, or 3.79 percent, supplied both code and data for replication, which is a warning about methodological confidence [S24]. Ownership should never be used as a substitute for architectural evidence or as a claim about an individual engineer’s indispensability.

### 8. Existing whole-repository documentation tools solve size by pruning, planning, or delegating; their grounding varies

#### DeepWiki

The hosted Devin DeepWiki implementation is not open source, so its internal selection algorithm cannot be independently inspected. Its official documentation says that it indexes a repository, generates pages and diagrams, and offers Low, Medium, and High effort levels. It documents a large-repository control file, `.devin/wiki.json`, that bypasses the default cluster-based planning and lets the user specify pages. The documented limits are 30 pages, or 80 for enterprise, 100 notes, and 10,000 characters per note [S25]. The stated failure mode is partial documentation: important components may be missing when only some folders receive pages; the documentation recommends adding a page for each important folder. This is an honest indication that the hosted product treats page coverage as a planning problem, but it gives no public evidence that its default clusters correspond to architectural boundaries.

DeepWiki-Open is inspectable and should not be confused with the hosted product. Its repository configuration excludes common virtual-environment, node-module, VCS, vendor, build, distribution, and documentation trees, along with lockfiles and environment/configuration files in its default filters [S26]. Its RAG pipeline recursively reads eligible files, skips files above a configured 81,920-token limit, tracks lines, splits text with a configured 350-unit chunk and 100-unit overlap, embeds the chunks, and retrieves a top 20 set from FAISS [S27]. Its wiki generation passes a file tree and README to a model, then uses RAG while generating pages. I found no AST, import graph, call graph, change-coupling, or ownership ranking in this path. The practical strategy is therefore extension/path filtering plus file-chunk retrieval and model-written pages.

The source also shows concrete failure behavior. Wiki-page generation retries twice and then emits an error-placeholder page; malformed or truncated structured output is salvaged with regular expressions. Citation post-processing turns references into repository URLs but does not check that a line exists or that the prose is entailed by the cited code. Its codemap path is stronger: the model supplies a verbatim snippet, the implementation finds that snippet in the cloned file, and the system replaces the guessed location with the found range [S28]. That verifies location for a code-map item, not the semantic truth of the description. The README warns that very large repositories may fail, which is consistent with the source’s aggregate filtering and bounded per-file behavior.

#### PocketFlow Codebase Tutorial

PocketFlow’s open-source tutorial pipeline uses glob-based inclusion and exclusion, excludes tests, docs, examples, build, and legacy paths by default, limits each file to a default 100,000 bytes, and caps the number of abstractions at ten [S29]. The crawler applies the per-file rules but has no aggregate repository budget [S30]. The flow is sequential: fetch files, identify abstractions, analyze relationships, order chapters, write chapters, and combine the tutorial [S31].

The important source-level detail is that `IdentifyAbstractions` concatenates all selected files into one model context and asks for the top five to ten abstractions. Validation checks YAML shape and valid file indices. `AnalyzeRelationships` receives abstraction descriptions and selected full files, then asks the model for summaries and edges. Validation checks schema and indices; it does not check an edge against an import or call graph. The final Mermaid graph is consequently model-authored. Files skipped by the crawler are not represented as unexplored areas, and the aggregate prompt can still exceed a model’s context even though each individual file is below the size limit. Its failure mode is silent omission plus unverified synthesis.

#### LangChain OpenWiki

OpenWiki takes a different approach. Its repository runner creates conceptual page jobs with a path, title, purpose, seed paths, related pages, and instructions. The planner prompt tells the worker to inspect manifests, major directories, entry points, public surfaces, end-to-end flows, state and persistence, failure handling, configuration, operations, integrations, and tests, while avoiding an exhaustive inventory [S32][S33]. In the code-mode source I inspected, there is no prebuilt AST/import/call graph or embedding index. Instead, a worker uses `ls`, `glob`, `grep`, and read operations, expands through callers, callees, state owners, integration boundaries, and tests, then submits a page [S34]. Ignored paths prevent unbounded root globbing.

OpenWiki’s strongest feature is its durable claim model. A page stores Markdown plus Grounded Claims with canonical `repo://` evidence, source version, exact line ranges, and hashes; a run can resume after a crash, and source drift interrupts or invalidates stale evidence [S35]. That is a materially better provenance strategy than a bare URL. It still proves primarily that the evidence location exists and was attached to the claim. A line-range check is not a semantic proof that the claim follows from the lines, nor does it prove a call path or module boundary without an analyzer.

#### CodeWiki as a comparable open-source approach

PorunC/CodeWiki adds more repository-wide structure before generation. Its analysis pipeline scans deterministically, parses AST nodes, builds a graph, performs community detection, and then indexes graph nodes and chunks for GraphRAG. Chunks retain path, start and end positions, hashes, and token counts [S36]. Its documentation says source references are validated before a page becomes `generated`; invalid references leave a draft, and invalid Mermaid is filtered. This is a useful pattern for evidence lifecycle and graph-aware retrieval. Community detection is still a clustering result, not proof of an architecture described by a human maintainer, and the public source does not establish semantic entailment checking for every sentence.

The common pattern across these tools is clear. They reduce size with path filters, file-size limits, fixed chunking, retrieval, page planning, or worker delegation. Only the more claim-oriented systems preserve a versioned evidence object. None of the inspected implementations provides a complete mechanical proof of the architecture prose. Sparring should retain their useful compression patterns but make coverage and failed verification first-class output.

### 9. A summary tree helps coherence, but it is not a safe evidence hierarchy by itself

There is direct evidence that hierarchical summarisation is useful for long documents. BooookScore evaluates summaries of books longer than 100,000 tokens using 1,193 fine-grained human annotations over eight coherence error types. In its GPT-4 comparison, hierarchical map-reduce summaries produced 353 counted errors versus 840 for incremental summaries. At the sentence level, entity omission fell from 7.3 percent to 3.71 percent and causal omission from 2.75 percent to 1.21 percent; hierarchical summaries were more coherent but less detailed [S37]. The authors explicitly say that source length made faithfulness difficult to measure. Thus, fewer coherence errors are not evidence that a hierarchy preserved all facts.

The 2025 ToM study describes the failure mode directly: independent MapReduce chunks break long-range dependencies and interconnections. Its DocTree method aggregates upward while recursively communicating across sibling branches to resolve conflicts. On its information-seeking tasks, it reported GPT-4o results of 41.17 F1 on inference QA and 85.0 percent on inference multiple choice; Qwen2.5-72B reached 30.17 F1 and 71 percent; DeepSeek-V3 reached 38.60 F1 and 77 percent. It reported a 15.8-point improvement on a dialogue-history QA task [S38]. The paper also warns that query-aware compression can omit intermediate information required for complex multi-hop reasoning and that chunk granularity remains a risk.

For a codebase, a wrong leaf summary can be copied into a module summary and then into a system sentence with no visible indication of where the error entered. The more dangerous case is not a wrong file description but a missing cross-cutting fact: authentication, transaction boundaries, error propagation, feature flags, tenancy, generated code, or deployment assumptions may be distributed across many files and belong to no single leaf. The hierarchy will tend to lose such facts if it only merges file summaries. Multi-document summarisation research provides a caution but not a code-specific measurement: one 2025 study reported up to 75 percent of generated content as hallucinated in some multi-document settings, including nonexistent topics fabricated by several models [S39]. That domain is news and conversation, so the number should not be transferred to code surveys.

No primary study located here measures a probability of code-architecture error compounding as a function of tree depth. The safe engineering conclusion is consequently stronger than the available measurement: treat the tree as a navigation and context-compression index, not as the authority. Keep leaf evidence and cross-cutting edges outside the prose tree. Re-check every parent claim against its child claims and, for high-impact bands, against raw source or analysis output. If sibling summaries conflict, preserve the conflict until a targeted inspection resolves it.

### 10. Model-generated claims need mechanical grounding, not only an evaluator or a citation

The code-summarisation literature gives measured warning signs. ProConSuL defines factual correctness as avoiding facts that are provably wrong from the supplied code, and hallucination as introducing nonexistent entities or unsupported invariants, guarantees, implicit behavior, usage, or external knowledge. In one 25-function benchmark spanning ffmpeg, OpenSSL, wrk, LLVM/Clang-Tidy, and libuv, GPT-4o was classified as factually correct on 22 functions with zero hallucinations under that evaluation. CodeLlama-7B had 22 correct and one hallucination; a ProConSuL-34B variant had 22 correct and one hallucination, while the untuned 34B baseline had 14 correct and nine hallucinations [S40]. The study also found that its GPT-4 proxy agreed with human labels imperfectly: for one proxy task precision was 0.769 and recall 0.714, and a sufficiency judgment agreed on 18 of 25 cases with seven ties. Small benchmarks and proxy judges should not be read as a guarantee for repository maps.

The FSE 2026 Hallu-Eval work reports a different stress test: Qwen2.5-Coder-7B hallucinated in 17 percent of original code-summary pairs but 97 percent of perturbed pairs; its detector reached F1 0.95, and a mitigation reduced one DeepSeek-Coder-6.7B rate from 66 percent to 59 percent [S41]. The benchmark is specifically about perturbed code and summary hallucinations, so it measures sensitivity to inconsistency rather than the ordinary rate for an unperturbed whole repository. It nevertheless supports testing the survey against adversarially altered or stale evidence.

Two newer benchmarks provide additional scale and task-specific rates. ETF’s CodeSumEval reports 411 summaries from seven language models and 9,933 entity-level samples. Its summary-level table labels 130 of 411 summaries, or 31.63 percent, as hallucinated when at least one entity is hallucinated; at entity level, 90.84 percent were correct, 3.05 percent incorrect, and 6.11 percent irrelevant. Its detector reached 73 percent F1 [S53]. This is a direct code-summary rate, but the inputs are CodeXGLUE snippets rather than repository-wide documentation, and the expensive human annotation was reduced to about ten percent of the collected data. RubberDuckBench asks repository questions derived from GitHub pull-request comments: across 20 LLMs, 58.3 percent of responses on average contained a rubric-defined lie, while the best overall accuracy was 69.29 percent [S54]. RepoReasoner uses dynamic pytest traces as call-chain ground truth over 14 Python repositories. Even with oracle files, its best call-chain result was 66.3 percent F1 and 21.3 percent exact match; its best output-prediction Pass@1 was 69.1 percent [S55]. These results make the case for a static or dynamic verifier especially strong for the map’s interaction edges.

Repository QA results are also below the reliability needed for unmarked learner claims. StackRepoQA’s approximately 58–64 percent range and CodeRepoQA’s low similarity scores show that answering a question from a repository is not the same as proving it. The source-grounded OpenWiki and DeepWiki-Open mechanisms improve traceability, but a URL or line range establishes provenance and location only. The verifier must check the proposition using deterministic repository facts.

The following checks are implementable and should be attached to every map sentence or band:

1. Snapshot check. Record the commit hash, worktree state, parser/analyzer versions, included and excluded paths, file and symbol counts, and unresolved generated or dynamic regions. Resolve every cited path with `git show <commit>:<path>`, confirm the line range is in bounds, and store the blob hash or span hash. A current line number without a commit is not durable evidence.

2. Boundary check. For a claimed module boundary, report the actual import, build, package, and call edges that cross it, internal versus crossing edge density, and the evidence from directory or manifest declarations. A boundary with many unexplained crossing edges is a candidate or a contested boundary, not a verified one.

3. Path check. For a claimed interaction, require a path in the static graph, or label every unresolved dynamic edge and downgrade the statement to possible. If runtime evidence is used, store the command, test, trace, configuration, and snapshot that produced it.

4. Constraint check. A band such as “all writes go through the repository layer” must have one or more grep-able or AST-queryable enforcement points: an API, type, decorator, middleware, policy, build rule, test, or configuration. The verifier should search for bypasses. If it finds only examples and no enforcement point, the statement is a hypothesis, not a constraint.

5. Entailment and contradiction check. Convert each generated sentence into atomic propositions. Check identifiers, referenced symbols, edge direction, and stated conditions against the graph and source spans. Search for contradictory implementations, alternate entry points, and tests that disprove the generalization. An LLM challenger may propose counterexamples, but it should operate over indexed evidence and return source locations rather than act as the judge.

6. Coverage check. Compute coverage by tracked module, entry point, graph edge class, and source bytes or symbols, with separate counts for inspected, excluded, unresolved, and intentionally sampled regions. A high retrieval score does not count as coverage. A map with a missing root or large unresolved cluster must expose that fact.

7. Execution check. Where safe, run the repository’s declared build, type check, tests, or a dry-run entry point and attach the result. Passing tests increase confidence in the exercised path; they do not verify untested architecture or prove that an absent edge does not exist.

The gate should fail closed for definitive claims. No sentence or band may be shown as verified unless its source locations resolve at the surveyed commit and its claim-specific structural checks pass. A failed or unresolved check must produce `contested`, `possible`, `stale`, or `unexplored`, never a normal-looking sentence with a weak citation.

### 11. Incomplete coverage should be visible as a state, not rendered as emptiness

Uncertainty estimates from language models are not reliable enough to use as the sole confidence signal. Kapoor’s NeurIPS 2024 study reports that a calibrated method reduced expected calibration error from 29.9 percent to 10.8 percent across six models, while finding that roughly 1,000 examples could be nearly as valuable as 20,000 for calibration [S42]. A 404-participant study of first-person uncertainty found that uncertainty language reduced agreement from 80.9 to 74.8 percent and confidence from 3.95 to 3.66 out of five while increasing accuracy from 63.9 to 72.8 percent [S43]. The agent’s verbal confidence should therefore be treated as a signal to calibrate and validate, not a truth probability.

Visualization research repeatedly finds that blank space is ambiguous. Robinson’s cartography analysis argues that an empty map can mean “nothing is there,” “nothing was measured,” or “the map is incomplete,” and recommends making absence visible [S44]. A 30-person visualization study comparing zero, omitted, and explicitly missing values found that explicit encodings improved recognition of missingness [S45]. Other work finds that simply removing a line obfuscates missingness, while glyphs, opacity, annotations, or a separate missing-data channel make it more legible [S46][S47]. The effect depends on the task; a review of 86 uncertainty-visualization studies covering 372 evaluation paths finds that evaluations overuse task performance and satisfaction and recommends measuring actual decisions and calibration [S48].

Open learner model work is directly relevant because the map describes a learner’s codebase understanding and invites correction. A review of learner-facing visualizations found uncertainty rarely represented directly and identifies multiple design choices for showing inconsistent evidence [S49]. A Java open-learner-model study with 46 enrolled students, 37 logged participants, and 32 valid cases found that showing system performance and student confidence separately improved both measures, with a reported effect size d = 1.02; the authors note the small, single-domain sample [S50]. Another study reports that accessed open learner models improved post-test performance, confidence, and use of the model, but the exact effect is context-dependent [S51]. The design implication is to show what the system knows, how it knows it, and what it has not inspected, while allowing the learner to challenge a claim.

The map should use a small, explicit state vocabulary:

- `verified`: the claim is supported by source and analysis evidence at the surveyed commit.
- `inferred`: the claim is a synthesis across verified evidence but is not itself a directly observed fact.
- `contested`: relevant evidence disagrees or competing interpretations remain.
- `possible`: the claim depends on unresolved dynamic behavior or runtime conditions.
- `stale`: the evidence refers to an earlier commit than the displayed repository.
- `unexplored`: the relevant region or evidence class was not inspected.
- `absent`: a defined search over a stated scope found no matching item; this is not the same as unexplored.

Use redundant encodings: text labels and a legend, plus hatching or a dashed outline for unexplored regions, a distinct border for contested regions, and a small commit or evidence indicator for verified regions. Do not rely on color or opacity alone. An unexplored cluster should remain visible as a node or group labelled “not inspected,” with counts such as “12 of 31 tracked modules examined.” If the survey finds no item in a searched scope, show the denominator and query, for example “no `@Transactional` annotation found in 18 inspected write paths,” rather than leaving an empty band. Clicking a node or band should open its evidence, coverage, unresolved edges, and last verification commit.

## Claims I could not verify

- I found no primary benchmark that evaluates a complete learner-facing repository architecture map against maintainer-verified nodes, bands, and cross-cutting constraints. Retrieval and QA benchmarks mostly use edited files, accepted answers, or task success as their labels.
- I found no codebase study that measures error propagation as a function of hierarchical-summary depth, such as a verified probability that a wrong leaf claim survives into a wrong system claim. The proposed re-checking of parent claims is an engineering control motivated by the observed failure modes, not a measured law.
- I could not inspect the implementation of hosted Devin DeepWiki. Its official documentation is primary evidence for its documented behavior and failure modes, but not for an undisclosed internal ranking algorithm.
- The exact dataset size and all experimental details of the FSE 2026 hallucination study were not available in the primary conference record I could inspect. I used only the rates and mitigation results stated in that record and treat them as a stress-test result, not a general repository-survey rate.
- I found no controlled study that establishes one universal visual convention for unexplored software-architecture regions, nor one calibration threshold that should block a map. The recommended states and gates are a conservative implementation design assembled from the cited visualization and open learner model evidence.
- The 2026 AIED abstract on uncertainty visualization reports a 1,653-participant within-subject study, but I did not verify the full paper or its complete effect sizes. I do not use it to justify a specific interface choice.

## Recommended approach

1. Freeze a survey snapshot. Record the repository commit, submodules, worktree changes, tool versions, language parsers, configuration profiles, and a complete inventory. Classify every path as inspected, excluded by rule, generated, binary, unresolved, or pending. Never allow an unlabelled omission.

2. Discover operational roots before reading deeply. Parse package and build manifests, workspace/module declarations, executables, CLI registrations, server factories, plugin entry points, CI jobs, deployment services, test runners, and public exports. Resolve each profile that can be enumerated. Mark environment-dependent roots as possible until corroborated.

3. Build deterministic evidence graphs. Use AST, LSP/SCIP, tree-sitter, compiler metadata, CodeQL, or language-specific analyzers for containment, imports, exports, inheritance, calls, data flow, tests, configuration, and build/deploy edges. Keep unresolved dynamic dispatch, reflection, generated code, and plugin loading as explicit unknown edges.

4. Propose module candidates from several views. Combine dependency clustering, directory and manifest structure, names and documentation, entry-point reachability, and graph cuts. For every candidate, calculate internal and crossing edge density and retain the supporting paths. Do not force a split merely to meet the twelve-node display budget; create a second level when no cut is defensible.

5. Allocate reading budget with a transparent priority vector. Prioritize root-reachable nodes, bridge nodes, public and configuration surfaces, high-impact constraints, representatives of every cluster, and recent stable change-coupling signals. Use PageRank and betweenness for triage, not as architecture labels. Use lexical, semantic, history, and graph-neighborhood retrieval in stages, with high-recall first passes and a stop or abstain decision when additional context is unlikely to add evidence.

6. Inspect candidates and cross-cutting neighborhoods. Read enough surrounding code to establish responsibilities, callers, callees, data ownership, error paths, tests, configuration, and bypasses. Run targeted queries for likely bands such as authentication, persistence, transactions, errors, feature flags, tenancy, serialization, and deployment. A band must be discovered across the graph, not assigned to whichever file happened to mention the term first.

7. Write atomic claims with provenance. Each node sentence, interaction, constraint, topic, and concept-card seed gets a stable claim ID, type, status, source path and line range, surveyed commit, blob/span hash, extractor or query, unresolved-edge list, and coverage contribution. Keep the raw evidence and child claims alongside every hierarchical summary. Derive initial concept cards only from verified or explicitly inferred claims, and show the evidence that a learner will be asked to understand.

8. Run the mechanical verification gate before rendering. Check that every path and line range exists at the named commit; that module claims match actual import/build evidence; that definite call paths exist in the static graph; that possible paths identify their unknown edges; that each constraint has a searchable AST, code, configuration, test, or build enforcement point; and that contradiction searches have no unresolved result. Recheck parent summaries against children and raw evidence for all top-level nodes and bands. A normal map is permitted only when each displayed definitive claim passes these checks. Otherwise downgrade it or omit the sentence.

9. Render the working-memory map. Keep approximately twelve nodes and six bands at each level. Show the selection reason and status on each node or band, with links to evidence and a second-level map for deeper clusters. Show confidence as calibrated status plus coverage metadata, not as an unsupported percentage from the model’s prose.

10. Render uncovered areas as visible uncertainty. Keep excluded, pending, unresolved, stale, and unexplored regions in the graph or in an adjacent coverage layer. Use a dashed outline or hatching with a text label such as “not inspected,” and show counts and scope. Never turn a skipped directory into an apparently empty module, and never turn “no match found in the inspected scope” into “no such mechanism exists.”

11. Invite correction and preserve the audit trail. Let the learner confirm, reject, or flag a node or band. On rejection, store the counterexample and rerun targeted retrieval and verification rather than silently editing the sentence. Re-survey when the commit changes, invalidating evidence whose blob or span hash no longer matches. The durable product is the map together with its evidence and coverage boundary, not the map image alone.
