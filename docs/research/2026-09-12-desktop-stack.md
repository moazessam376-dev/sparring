# Desktop stack for a local-first engineering learning application

Date: 2026-09-12. Question: which zero-runtime-cost technical stack should an open-source desktop application use across Windows, macOS and Linux for local lessons, drills, notifications, MCP access, SQLite state and Git-backed synchronization? Sources are numbered at the end. Primary documentation and primary issue reports are identified in the findings; secondary sources are labelled.

## Findings

### 1. Tauri is the better desktop shell, but its webview contract is the main engineering cost

Tauri 2 is the current major line. The official release index lists Tauri 2.11.5 for the Rust crate, released 2026-07-01; Tauri CLI 2.11.4, released 2026-06-28; the JavaScript API 2.11.1, released 2026-06-17; and the bundler 2.9.4, released 2026-06-28 [S1]. Tauri 2 reached stable release on 2024-10-02 [S2]. Its architecture is a Rust core hosting web content in the operating system's webview rather than shipping Chromium [S3, S4]. This is a materially smaller distribution model, but it makes the renderer a platform dependency.

The size evidence is directional, not a benchmark for this application. Tauri's start documentation says a minimal application can be less than 600 KB [S4]. On Windows, its WebView2 bootstrapper adds approximately 0 MB when downloaded at install time, an embedded bootstrapper adds approximately 1.8 MB, an offline WebView2 installer adds approximately 127 MB, and a fixed WebView2 runtime adds approximately 180 MB [S5]. Electron's official rationale says most Electron applications are over 100 MB because Chromium, V8 and Node.js are shipped with the application [S6]. These figures compare a minimal Tauri shell and Electron's vendor-reported application class, not equivalent feature-complete builds.

There is no primary, current, apples-to-apples memory benchmark for this application. The architecture predicts lower idle footprint for a simple Tauri app because the webview is shared with the operating system, while Electron creates Chromium processes, including a renderer process for each BrowserWindow [S3, S7]. Electron exposes process.getProcessMemoryInfo() and process.getSystemMemoryInfo(), with statistics in KiB, but the API documentation is a measurement interface, not a baseline [S8]. On macOS, Electron notes that residentSet is unavailable because of compressed memory and that private memory is more representative [S8]. A project decision should therefore benchmark its own lesson page, diagram, SQLite and MCP workloads on all three operating systems.

The inconsistency is concrete. Tauri uses WebView2 based on Edge/Chromium on Windows, WKWebView on macOS, and webkit2gtk on Linux; exact versions depend on the host system [S9]. A primary Tauri issue reports a Tauri 2.11.2 application on Windows 11 with WebView2 148.0.3967.83 getting ERR_CONNECTION_REFUSED after a page reload during an asynchronous command; the custom IPC protocol then failed permanently [S10]. A primary Linux issue reports a SIGSEGV in libwebkit2gtk-4.1.so.0 during client-side navigation on Pop!_OS 22.04 with an NVIDIA GTX 1070, driver 580.82.09 and WebKit2GTK 2.50.2, while the same site worked in a browser [S11]. Another primary issue reports a blank Tauri window on Fedora 43 with Sway/Wayland and WebKitGTK 2.50.5; forcing X11 and cleanup did not fix that report [S12]. A Debian 13/Xvfb report with WebKitGTK 2.52.3 required WEBKIT_DISABLE_COMPOSITING_MODE=1 to display content [S13]. A further primary AppImage report says a build made on Ubuntu 24.04 failed on Ubuntu 26.04/Mesa 25+ because bundled Wayland, GLib and GStreamer libraries conflicted with the target's WebKit helper; removing system libraries fixed the failure [S14]. On macOS, a primary Intel-Mac report describes a React form whose disabled state did not change inside Tauri although it worked in a regular browser [S15]. These are issue reports, not prevalence estimates, but they establish actual failure modes: GPU/compositing crashes or blanks on Linux, native-library compatibility failures in AppImages, asynchronous IPC failure after WebView2 reload, and at least one Intel WKWebView/frontend behavior discrepancy.

### 2. Tauri's native feature coverage fits this app better than Electron's built-ins

Tauri's notification plugin is version 2.3.3 as of 2025-10-27 [S16]. It exposes immediate native notifications on Windows, Linux and macOS; Windows notifications require an installed application, and development notifications use a PowerShell name and icon [S17]. The shared JavaScript type surface includes Schedule.at, Schedule.every and Schedule.interval, with recurrence units such as second, minute, hour, day, week, two weeks, month and year [S17]. That type surface is not enough to promise scheduled desktop delivery: the current desktop Rust implementation constructs an immediate notify_rust notification and does not consume the schedule field, while desktop sendNotification uses the browser Notification constructor [S99, S100]. For this app, schedule reminders with a resident tray process and a durable timer, or add an explicitly tested OS scheduler integration. The actual fallback APIs are Windows Task Scheduler 2.0 or schtasks.exe, macOS launchd LaunchAgents through Service Management, and Linux systemd.timer units [S101, S102, S103]. Do not describe the official Tauri desktop plugin as a native recurring-notification service.

The system tray is a Tauri core feature, enabled by the tray-icon Cargo feature. The Rust API is TrayIconBuilder and the JavaScript API is TrayIcon.new from @tauri-apps/api/tray [S18]. Autostart is the official tauri-plugin-autostart, version 2.5.1 as of 2025-10-27 [S19]. Its JavaScript surface includes enable, isEnabled and disable; on macOS its Rust launcher is MacosLauncher::LaunchAgent [S20]. Deep links are handled by tauri-plugin-deep-link version 2.4.9 as of 2026-05-02 [S21]. The JavaScript API includes getCurrent and onOpenUrl, and the plugin documents Windows, Linux and macOS registration [S22]. Linux AppImage registration depends on the installed launcher path, moving the AppImage invalidates the registration, and macOS runtime registration is unsupported; the scheme must be declared in configuration and the bundled application must be installed in /Applications for macOS testing [S22]. These caveats are operational requirements, not reasons to reject Tauri.

SQLite is supported by tauri-plugin-sql version 2.4.0 as of 2026-04-04 [S23]. The plugin's documented SQLite path is Database.load('sqlite:...'), with db.execute and db.select; it uses sqlx and supports SQLite, MySQL and PostgreSQL [S24]. It is an official integration, but the documentation does not promise a fixed binary-size cost or one universal system-library strategy. The release artifact should be tested on a clean machine for each platform.

The updater plugin is version 2.10.1 as of 2026-04-04 [S25]. It supports Windows, Linux and macOS, requires signed update artifacts, and documents AppImage plus signature files for Linux, .app.tar.gz plus signatures for macOS, and EXE or MSI plus signatures for Windows [S25]. Its static update manifest uses version, notes, pub_date and per-platform URL/signature entries [S25]. This gives Tauri a single documented update path across all three platforms.

### 3. Electron is more uniform in rendering, but leaves important app behavior to platform code

Electron 44.3.0 is the current stable release listed on 2026-09-08; it bundles Chromium 152.0.7977.78 and Node.js 24.20.0 [S26]. Electron's rendering surface is more consistent because it ships Chromium, at the cost of the larger distribution and Chromium multi-process model [S6, S7]. Electron is therefore the safer choice if pixel-identical browser behavior is worth paying the size and memory cost, but this application does not need a bundled browser engine to run a coding agent or SQLite.

Electron's Notification class provides immediate notification.show() calls [S27]. The official API and tutorial do not document scheduled or recurring notifications. Windows requires a Start Menu shortcut with an AppUserModelID and ToastActivatorCLSID; macOS requires code signing; Linux uses libnotify [S27]. Scheduling would require an OS-specific scheduler, a native module or a resident-process timer, as it does for Tauri's current desktop implementation. Electron's Tray class covers macOS menu-bar extras, the Windows notification area and desktop-environment-dependent Linux trays [S28]. app.setLoginItemSettings covers macOS and Windows, with macOS reliability tied to a packaged, signed and notarized application [S29]. Electron's setAsDefaultProtocolClient, removeAsDefaultProtocolClient and isDefaultProtocolClient cover macOS and Windows; Linux needs a .desktop handler [S29].

Electron has no built-in SQLite product. The official packaging documentation says Electron Core provides no packaging tooling and recommends Electron Forge; the native-code documentation says native Node add-ons must be rebuilt for Electron and packaged correctly [S30]. A project can use a Node SQLite library such as better-sqlite3, but it owns the native-addon ABI and distribution work. Electron's autoUpdater supports macOS and Windows, not Linux; Linux updates are delegated to the package manager [S31]. The official update tutorial's update-electron-app and update.electronjs.org service are free for qualifying public GitHub repositories and GitHub Releases, but they cover macOS and Windows and require macOS signing [S32]. Tauri is therefore the better fit when one maintainer needs one all-platform updater and immediate-notification integration; neither shell supplies a verified, uniform scheduled-desktop notification service.

### 4. Wails is serious, but Wails 3 is still beta; other 2025-2026 experiments are not ready

The Wails project announced Wails 3 Beta on 2026-08-02 and explicitly says that Wails 2 remains the current stable line receiving fixes; the Wails 3 desktop API is intended to be stable but should be tested thoroughly [S33]. Wails uses native platform webviews and Go, so it has the same broad renderer inconsistency category as Tauri. Its current Linux installation requires GCC, GTK4 and webkitgtk-6.0; the legacy GTK3/WebKit2GTK 4.1 path is retained with a gtk3 build tag until Wails 3.1 [S34]. It is worth tracking for a Go codebase, but beta status is a plain reason not to make it the foundation of this app in September 2026.

Tauri's March 2025 Verso integration is an experimental Servo-based browser option, not a stable replacement for the operating-system webviews [S2]. I found no newer 2025-2026 framework with a stable, documented combination of native scheduled notifications, tray, autostart, SQLite, all-platform updates and deep links that is a better-maintained fit than Tauri 2. Electron remains the serious uniform-rendering alternative; Wails 3 is the serious emerging contender, but not ready for this baseline.

### 5. Shipping signed and auto-updating binaries costs money on macOS, while Windows has viable free paths for qualifying open source

Apple's Developer Program costs 99 USD per membership year; Apple says local currency and taxes can vary [S35]. A free Apple account is not the route to Developer ID distribution and notarization. The normal macOS flow is to enroll, obtain a Developer ID Application certificate, sign the app with a hardened runtime and secure timestamp, package the app as a ZIP/DMG/PKG, submit with notarytool, wait for a result, and staple the ticket with stapler. Apple's notarization requirements say the service requires a current notarization workflow and no longer accepts altool or Xcode 13-or-earlier submissions; the signed app must not contain get-task-allow=true [S36]. Apple's command-line example is xcrun notarytool submit followed by stapling, and its CI guidance supports an API key or keychain profile [S37]. Gatekeeper can validate a stapled ticket offline or obtain the ticket online [S36]. Apple Developer ID signing documentation identifies Developer ID Application as the external-distribution certificate [S38]. The unavoidable maintainer cost for a conventional notarized macOS release is therefore the 99 USD annual membership, before any CI or certificate-management costs.

Windows signing changed when the CA/Browser Forum required code-signing private keys to be held in a hardware cryptographic module, cloud HSM or signing service from 2023-06-01 [S39]. Cheap software-only certificates are not the compliant path. Microsoft's current options page lists OV certificates at approximately 150-300 USD per year and EV certificates at 400 USD or more per year; it says the OV/EV reputation model no longer provides a SmartScreen instant bypass [S40]. Azure Artifact Signing, formerly Trusted Signing, is advertised at 9.99 USD per month for Basic with up to 5,000 signatures and 0.005 USD per additional signature; Premium is advertised at 99.99 USD per month for up to 100,000 signatures and the same excess-signature price [S41]. The service requires a paid Azure subscription, does not issue EV certificates and keeps keys in the service [S42]. SignPath Foundation offers free code signing for qualifying open-source projects: the project must meet its OSI-license and maintenance/release requirements, and release signing is subject to its approval, MFA and code-policy conditions [S43, S44]. For this app, SignPath is the credible zero-maintainer-cost Windows path if the project qualifies; Azure is the predictable paid path.

SmartScreen uses publisher reputation and file-hash reputation. Microsoft's primary documentation says even a validly signed new binary can warn until reputation is established, that an unsigned download shows “Windows protected your PC” with a possible Run anyway path, and that enterprise policy can block it [S45]. A new EV certificate no longer bypasses the warning, and Microsoft says reputation may take several weeks and hundreds of clean installs [S45]. A signed release therefore improves publisher identity and trust but does not make a brand-new app warning-free.

For Linux, Tauri's current distribution documentation lists Debian, Snap, AppImage, Flatpak, RPM and AUR formats [S98]. Its updater is designed around AppImage on Linux [S25]. Lead with AppImage for the maintainer-owned, self-updating artifact, publish a DEB for Debian/Ubuntu users, and add Flatpak when sandboxed permissions and Flathub distribution are worth their review overhead. Linux signing and trust are distribution-specific; there is no single Linux analogue to Apple's Developer ID plus notarization flow in this stack.

On a public GitHub repository, standard GitHub-hosted ubuntu-latest, windows-latest and macos-latest runners are free and unlimited; self-hosted runners are also free [S46]. The documented public-repository limits include 20 concurrent jobs in total, at most 5 concurrent macOS jobs and a 6-hour maximum per job [S47]. Larger GitHub-hosted runners remain chargeable even for public repositories [S46]. GitHub Releases allow up to 1,000 assets per release, each under 2 GiB, with no documented total release-size or bandwidth limit [S48]. A release workflow can therefore build the three platforms, sign with Apple credentials and a Windows signing service or SignPath integration, notarize macOS, create Tauri updater artifacts and publish release metadata without paying for GitHub Actions on a public repository. Apple membership, Windows signing service/certificate and any hosted signing account are separate costs.

### 6. The desktop app should expose MCP over Streamable HTTP on loopback

The current MCP specification revision is 2026-07-28, published 2026-07-28 [S49, S50]. MCP uses JSON-RPC 2.0 and standardizes servers exposing tools, resources and prompts; the 2026 specification also defines an extensions mechanism and tasks-related work [S49]. The standard transports are stdio and Streamable HTTP [S50]. Stdio is for a client spawning a subprocess and exchanging newline-delimited JSON-RPC. Streamable HTTP uses one HTTP endpoint, normally /mcp, with client requests sent by POST and each response returned as JSON or request-scoped Server-Sent Events.

HTTP+SSE is deprecated for new implementations. The transport specification says Streamable HTTP replaced the old HTTP+SSE transport introduced in the 2024-11-05 revision and that new implementations should not adopt the legacy transport; a client may fall back for compatibility [S51]. In the current revision, a server does not need a long-lived GET stream or protocol-level session. Long-lived server notifications can use a subscription stream, but the normal request is an independent POST. This suits a desktop app that stays running in a tray: the app owns a local HTTP listener and the agent connects when needed, without requiring the agent to spawn a second copy of the app. Stdio remains the better choice when an agent's configuration only supports process spawning.

The current TypeScript SDK v2 documents the 2026-07-28 protocol line; the observed @modelcontextprotocol/client package release is 2.0.0 [S52]. The app can create a Streamable HTTP server endpoint and keep the lesson/graph operations behind typed MCP tools. A client configuration is ordinary agent configuration: Claude Code accepts claude mcp add --transport http name http://127.0.0.1:PORT/mcp and a JSON entry with type http and url; OpenCode accepts opencode mcp add name --url https://.../mcp and a remote server with url, headers or oauth; VS Code's MCP configuration uses a servers object with type http, url and headers [S53, S54, S55]. The app should publish a generated configuration snippet rather than assume that all agents use the same file.

The security minimum is specific. The Streamable HTTP specification requires Origin validation, recommends binding local servers only to 127.0.0.1 rather than 0.0.0.0, and warns about DNS rebinding [S51]. HTTP authorization is optional in MCP generally, but HTTP implementations should follow the authorization specification; stdio implementations should use environment or platform credential mechanisms instead [S56]. For a single-user desktop server, generate a random high-entropy bearer token per installation or per server start, store it in the OS credential store, require Authorization: Bearer, validate Origin and bind to loopback. This token design is an implementation recommendation derived from the protocol's bearer-auth and loopback guidance, not a protocol-mandated localhost scheme. Never accept a token in the query string. For remote or multi-user deployment, implement MCP's OAuth 2.1 resource-server flow and protected-resource metadata instead of inventing a desktop token protocol [S56].

### 7. A small typed lesson schema is a better core than an existing learning-content standard

xAPI 2.0 is an event and learning-record interoperability specification, not a lesson rendering format [S57]. cmi5 is an xAPI profile for LMS-launched assignable units, with launch, authentication, session and reporting rules; its course/assignable-unit model is useful export vocabulary but assumes an LMS relationship [S58]. QTI 3.0 is a final assessment-interchange standard for items, tests, results and delivery across authoring tools, item banks, platforms and assessment engines [S59]. QTI is worth stealing for quiz item semantics and answer processing, not for this application's complete lesson document.

H5P Course Presentation is a slide-like content type with titles, links, images, audio, video, quiz types and a final test; H5P also has content types such as Interactive Video, Branching Scenario, Flashcards, Essay and Drag and Drop [S60]. It is useful prior art for mid-lesson checks and branching, but the runtime and content-type package model are larger commitments than a local-first typed document. H5P is better treated as an import/export boundary for interactive exercises, not as the internal source of truth.

MDX 3.1.1 is the current MDX release listed by the official repository, released 2025-08-29 [S61]. MDX combines Markdown with JSX, JavaScript expressions and imports/exports, then compiles to JavaScript; components can override HTML rendering [S62]. That is attractive for hand-authored lessons, but an AI-generated MDX document is executable code unless the application builds a strict sandbox and import allowlist. The execution model is documented; the security conclusion is an engineering inference.

Markdoc 0.5.9 is the latest release listed by its official repository [S63]. It is Markdown-based, supports custom tags with typed attributes and validation, and exposes parse and validate operations that return structured validation errors [S64, S65]. Markdoc is the most reusable authoring syntax here if the application wants human-editable text, but only with a closed tag allowlist and no arbitrary component loading. MyST is a CommonMark superset with block directives and inline roles, including callouts, tabs, figures and embedded charts [S66]. MyST widgets use anywidget JavaScript modules and its documentation warns to load only trusted widgets; in-page execution is beta and depends on Jupyter backends [S67]. That makes MyST valuable for notebook publishing, but unnecessarily broad for an offline engineering lesson.

The core document should therefore be a versioned JSON schema owned by the app, with typed blocks such as prose, code, diagram, interactiveCheck, quiz, explanation and reference. The agent emits JSON validated against that schema; Markdown is a string inside prose blocks, not the document's execution model. Adopt QTI-like item fields for quiz choices, response processing and feedback; borrow xAPI-like event vocabulary for local drill records; optionally provide a Markdoc import/export adapter. The app controls every interactive component and can migrate the schema without migrating an LMS or JavaScript runtime.

### 8. Mermaid first, D2 selectively, Graphviz as a deterministic fallback

Mermaid's official release repository lists mermaid 12.0.0, released 2026-09-10 [S68]. The release is breaking, requires ES2024 and modern browser/runtime baselines, and changes defaults including ELK layout and the redux-color/neo appearance options [S68]. Mermaid supports the diagram families most relevant here, including flowchart, sequence, class, state, entity-relationship, mindmap, timeline, architecture, GitGraph, C4, Kanban, Sankey, radar, treemap, Venn, Ishikawa and Wardley diagrams [S69]. Its programmatic API exposes mermaid.parse for syntax validation and mermaid.render for SVG output, returning bindFunctions for wiring interactions [S70]. This gives an agent-generated string a cheap validation and repair loop before display.

D2 0.9.0 is the current release listed by the official repository, released 2026-09-07 [S71]. D2's primary documentation covers text-to-diagram input, multiple layout engines, themes, sketch mode, containers, code snippets, Markdown, class and sequence diagrams, interactive links/tooltips and SVG/PNG/PDF/PPTX/GIF/ASCII export [S72]. Its default layout is Dagre; ELK and TALA are alternatives, with TALA aimed at software architecture [S73]. D2 is a strong second language for architecture diagrams where autoformatting and layout-engine choice matter, but its browser embedding and export pipeline are more involved than Mermaid's direct render-to-SVG path.

Graphviz 16.1.0 is the current stable source release [S74]. DOT has a compact grammar, and the dot layout engine is specifically hierarchical/layered for directed graphs, with objectives including reducing edge crossings and edge length [S75, S76]. The @hpcc-js/wasm package supplies Graphviz compiled to WebAssembly; its current package release is 2.35.1, while its repository documents a bundled Graphviz 15.1.0, so it is not automatically the same as the current native Graphviz release [S77, S78]. Graphviz WASM is an excellent deterministic fallback for dense dependency graphs, subject to its bundle size and version lag.

Excalidraw's public API is scene-oriented: an imperative API exposes updateScene, getSceneElements, applyDeltas and mutateElement [S79]. Its latest release is 0.18.1, released 2026-04-21 [S80]. tldraw represents shapes as validated JSON records with type, coordinates and props; its Editor API includes createShape, updateShape and createShapeId, and its AI documentation describes language models creating shapes through editor.createShape [S81, S82]. These are good app-canvas APIs when the agent is asked to produce explicit shape data, but they require coordinates, IDs, props and layout decisions. They are less likely than a declarative diagram language to produce a correct first draft from a short prompt.

There is no controlled primary benchmark comparing first-attempt language-model accuracy or aesthetics across these tools. The evidence supports an engineering inference: make Mermaid 12.0.0 the default because it has compact declarative syntax, broad software-diagram coverage and parse/render validation; use D2 0.9.0 for architecture diagrams that benefit from its layout engines and themes; use Graphviz WASM for predictable dense directed graphs; reserve tldraw or Excalidraw scene JSON for diagrams that users must edit as native shapes [S68, S71, S79, S81]. A render-validate-repair loop is more defensible than assuming any model will produce good geometry on its first attempt.

### 9. SQLite is sufficient for the local graph and should remain a derived cache

SQLite 3.53.4 is the current release listed by the official project, dated 2026-07-24 [S83]. SQLite is self-contained and public-domain [S83]. For a single user's projects/topics/edges and drill history, SQLite is sufficient for indexed lookups, joins and graph traversals; the exact upper bound for this app is not established by a benchmark, so large-scale graph analytics or multi-user concurrent writes would be a separate design problem.

SQLite's WITH clause supports ordinary and recursive common table expressions for hierarchies and graphs. The official documentation gives graph-connectivity examples and explains the recursive-term restrictions; it also warns that UNION versus UNION ALL determines whether repeated rows are eliminated, and recommends a LIMIT as a safety bound for recursive queries [S84]. A graph query can therefore traverse prerequisites, related topics and project dependency paths without a graph database. Use indexes on edge endpoints, bound traversals, and retain a visited-set strategy in the recursive query where cycles are possible.

Tauri's SQL plugin supplies migration tooling: a migration has a version, description, SQL and Up/Down kind; migrations are registered with add_migrations and applied by the database loader. The docs state that migrations run in atomic transactions, have unique versions and can safely be rerun [S24]. Keep the SQLite schema disposable: the event reducer creates it from the log, migrations make upgrades fast, and a rebuild command remains the recovery authority.

### 10. Git-backed event sync is plausible, but Git is not an event log protocol

GitJournal is prior art for a mobile-first note application whose notes are stored in a Git repository of the user's choice, including GitHub, GitLab or a custom remote [S85]. The Obsidian Git community plugin is secondary prior art for scheduled pull, commit and push, startup pulls and conflict workflows [S86]. These examples show that Git can be an acceptable user-owned synchronization backend for text-oriented local applications; they do not prove that Git is a robust general-purpose sync database.

The proposed append-only JSON Lines model is sound only if the event model carries the guarantees Git does not. Give every event a globally unique event ID, device ID and monotonically increasing per-device sequence; make the reducer idempotent; store schema version and payload type; and treat Git commit order as transport history, not causal order. Per-device files reduce two devices appending to the same file, but they do not eliminate branch divergence, remote resets, credential expiry, repository latency or repository-size growth.

The primary Git failure mode is non-fast-forward push: git push rejects a remote update that is not a fast-forward by default, and the user must fetch then merge or rebase [S87]. Never force-push the sync branch. The reducer should tolerate duplicate events because retries can replay a commit. Import should validate each JSON line, quarantine malformed lines and continue only when the missing event is explicitly surfaced. The writer should use a temporary file, flush/sync it and atomically rename before committing. A single sync worker needs a repository lock because concurrent Git processes can corrupt or contend on the worktree/index.

Other engineering failure modes are consequences of the design rather than promises in Git's documentation: Git commit order cannot resolve two offline edits that encode contradictory state; a device filename must be a stable ASCII identifier because case-insensitive filesystems can collide; an ever-growing event history will eventually require chunking and a carefully versioned snapshot/checkpoint; a remote reset or force-push can hide unseen history; and attachments should not be put into unbounded JSONL. A deterministic merge policy, hash-linked checkpoints and an exportable backup branch are prudent. None of these should be disguised as a guarantee that Git provides conflict-free sync.

### 11. Authenticate to GitHub through OAuth or the system credential manager

GitHub's OAuth documentation supports authorization-code and device-authorization flows. For a native desktop app, use a loopback redirect with authorization code plus PKCE when a browser is available; GitHub identifies native apps as public clients that cannot protect a client secret and recommends PKCE over device flow when possible [S88, S89]. If a headless or constrained environment needs device flow, GitHub's device code expires after 15 minutes (900 seconds) and the client polls POST https://github.com/login/oauth/access_token [S88]. The application should open the browser, receive the callback or show the device code, and never ask the user to paste a personal access token.

For generic Git remotes, prefer invoking the user's system Git with Git Credential Manager when it is installed. GCM supports Windows, macOS and Linux, browser/device OAuth and secure platform credential storage [S90]. Otherwise implement GitHub's PKCE/device flow, store the resulting credentials in the platform keychain or credential manager, request the narrowest repository scope, refresh or reauthorize when required, and keep synchronization queued while offline. A self-hosted Git server can use SSH keys or its own OAuth flow; the app should not assume that every remote is GitHub.

### 12. Telemetry should be opt-in, minimal and self-hostable

Matomo On-Premise is a mature self-hosted analytics option: it is free to download, keeps data under the operator's control and documents privacy/GDPR configuration; its core tracker and core platform are GPLv3 [S91, S92]. Plausible Community Edition is an AGPLv3 self-hosted deployment distributed with Docker Compose; its official repository warns that the stack recommends at least 2 GB of RAM because it uses ClickHouse [S93, S94]. Matomo is the more established and featureful choice but carries more operational surface; Plausible has a smaller product surface but is still a server deployment rather than a zero-cost hosted endpoint. I did not find a current primary self-hosting deployment document strong enough to recommend PostHog for this maintainer's minimal telemetry service.

The GDPR applies when telemetry is personal data, which can include an online identifier, device or installation identifier, IP address, timestamp or usage event that can be linked to a person. The controller needs an Article 6 legal basis; consent must be demonstrable, specific, informed and as easy to withdraw as to give under Article 7; Article 13 requires notice of purposes, legal basis, recipients, retention and rights [S95]. For an open-source desktop app, the clean implementation is a first-run, off-by-default opt-in with separate purposes, no project names, lesson text, code, Git URLs or MCP content, a resettable random installation ID, short retention, in-app disable/delete, and a privacy notice shipped with the app. Consent and withdrawal should themselves be recorded locally, not uploaded until the user has opted in.

The ePrivacy Directive's Article 5(3) covers storing information in or accessing information from a user's terminal equipment. It permits this when necessary for transmission or for a service explicitly requested by the user, and otherwise requires clear information and a right to refuse; the European Commission's 2025 staff document summarizes this as consent in most cases and notes that national transposition varies [S96, S97]. In a desktop app, an analytics SDK that writes or reads a nonessential installation identifier or local analytics state can therefore raise the same terminal-equipment issue; it is not limited by the word “cookie” or by websites. Pure outbound telemetry that does not store or read nonessential terminal information may fall outside Article 5(3), but GDPR can still apply to the transmitted personal data. The legally conservative product decision is opt-in consent, data minimization and an implementation review against the user's Member State law.

## Claims I could not verify

- I found no current primary apples-to-apples benchmark for Tauri versus Electron memory or complete application bundle size using this app's workload. The size figures above are vendor-reported examples, not a performance result.
- Electron's current official Notification API documents immediate display but does not document a built-in scheduled or recurring notification API. I cannot prove that no third-party module or platform integration exists.
- I found no 2025-2026 framework release with a primary-source-verified, stable cross-platform feature set that displaces Tauri for this app. Wails 3 was explicitly beta on 2026-08-02 [S33].
- I found no controlled primary benchmark of language-model first-attempt correctness or visual quality for Mermaid, D2, Graphviz, Excalidraw and tldraw. The diagram recommendation is an engineering inference from their documented input languages, validation and layout APIs.
- I found no evidence establishing a safe event-log size, snapshot interval or merge policy for this exact Git-backed application. Those values require a prototype with offline and divergent-history tests.
- The GDPR/ePrivacy discussion is a technical compliance interpretation, not legal advice. Whether a particular desktop telemetry implementation triggers Article 5(3) depends on what it stores or accesses and on the Member State's implementing law.
- I did not verify a current official PostHog self-hosting deployment specification suitable for this small, maintainer-free telemetry service, so it is not in the recommendation.

## Recommended stack

1. Desktop framework: Tauri 2.11.5 [S1], with a documented Linux support matrix and WebView2 bootstrapper. Reason: official all-platform immediate notifications, tray, autostart, SQLite, updater and deep-link integrations with a small shell. Strongest argument against: WebKitGTK and OS-webview differences create real Linux failures, and scheduled reminders need an additional resident-process or OS-scheduler design [S99, S100].
2. Packaging and signing: GitHub Actions on public standard runners; AppImage plus DEB on Linux; Apple Developer Program plus Developer ID/notarization on macOS; SignPath Foundation for qualifying Windows open source, with Azure Artifact Signing as the paid fallback. Reason: the build and release automation is free on public GitHub, and there is a zero-price Windows signing route for eligible projects. Strongest argument against: notarized macOS distribution still costs 99 USD per year [S35], and SmartScreen reputation still starts at zero [S45].
3. MCP: a loopback Streamable HTTP server at 127.0.0.1 [S51] with a random bearer token in the OS credential store, plus an optional stdio adapter. Reason: Streamable HTTP is the current transport and avoids spawning duplicate desktop processes. Strongest argument against: agent configuration and local auth behavior still vary, so a stdio fallback is necessary.
4. Lesson document: a versioned, typed JSON schema with Markdown prose and closed interactive block types; borrow QTI response semantics and xAPI event vocabulary; optionally import/export Markdoc. Reason: the app controls execution, validation, migration and offline rendering. Strongest argument against: the project owns a schema and tooling instead of inheriting broad interoperability from an existing standard.
5. Diagram rendering: Mermaid 12.0.0 [S68] as default, D2 0.9.0 [S71] for architecture layouts, and Graphviz WASM as a deterministic dense-graph fallback; validate and repair before display. Reason: declarative text plus parser/render APIs gives an agent the smallest correction loop. Strongest argument against: Mermaid 12.0.0 is a breaking current release and the three renderers add asset and compatibility cost.
6. Local data: SQLite 3.53.4 [S83] with recursive CTEs, indexed edge tables and Tauri SQL migrations; rebuildable schema cache. Reason: recursive graph queries and transactional local storage are already in the database engine. Strongest argument against: recursive SQL needs cycle bounds and careful query design, and SQLite is not a multi-writer sync engine.
7. Sync and GitHub auth: per-device JSONL event files, idempotent reducer, deterministic IDs, non-force-push fetch/merge loop, system Git plus Git Credential Manager, and OAuth PKCE/device fallback for GitHub. Reason: user-owned remotes and platform credential stores preserve local-first ownership without pasted secrets. Strongest argument against: Git divergence, repository growth and credential failures become product features that must be tested and explained.
8. Telemetry: off by default, explicit opt-in, event allowlist, no source/project content, resettable ID, deletion controls, and a self-hosted Matomo endpoint. Reason: mature self-hosting and conservative consent behavior fit an open-source app. Strongest argument against: the maintainer must operate a server, and opt-in data will be sparse.
